## 根因与前次验证不足

`_queue_structural_word_text_range_edit` 遇到目标换行或源软换行时，在 `replacement_token.anchor_element` 前直接创建译文 run，然后清空原字符范围。anchor 是整个 run，可能同时包含更早的多个句段；从其内部开始的后句会被提前到 run 开头。

上轮修复覆盖分页语义、富文本标记展开、句段消费数量和原文块归属，遗漏了普通文本换行替换路径。上轮合成目标标记没有保留真实译文中的换行，无法证明这一分支的位置正确；“在同一个原文块且内容完整”也不能证明块内句序正确。本记录纠正此前对图二问题验收不足的结论。

## 修复与失败策略

1. 换行替换先按真实字符偏移写入内部文本标记，记录原生参考样式；排队阶段不在整个 run 前插入译文。
2. 完成全部 token 文本编辑后，从当前 XML 子树定位标记，在标记所在的准确字符位置拆分 run。
3. 原位插入译文 `w:t`/`w:br`，保留后半 run 中的其他句段、分页、图片和样式，再继续处理后续标记。
4. 多个换行目标、同一 `w:t` 的多个替换以及同一 run 的多个 `w:t` 共用该路径。
5. 标记无法定位或节点不能安全拆分时中止导出；文件最终检查也覆盖新文本标记，避免残留进入用户文件。

不修改客户原文或译文来规避问题；已有导出文件保留为证据，新任务生成修复后的文件。
